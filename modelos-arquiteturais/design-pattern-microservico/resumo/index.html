Outros Padrões

Tags:
  • Api Gateway
Categories:
  • Modelos Arquiteturais

  3 minute read  

Os principais padrões de design para microserviços ajudam a lidar com desafios comuns como comunicação, escalabilidade, resiliência e segurança. Aqui estão os mais relevantes, além do Saga, que é usado para coordenação de transações distribuídas:

1. Padrões de Comunicação

API Gateway

  • Um único ponto de entrada para os clientes, roteando requisições para os microserviços corretos.
  • Pode lidar com autenticação, cache, rate limiting e balanceamento de carga.
  • Exemplo: O Netflix Zuul e o Kong API Gateway são implementações comuns.

Backend for Frontend (BFF)

  • Similar ao API Gateway, mas otimizado para diferentes tipos de clientes (web, mobile, IoT).
  • Cada tipo de cliente pode ter um backend específico que adapta a resposta conforme necessário.

Service Mesh

  • Gerencia comunicação entre serviços, adicionando monitoramento, segurança e controle de tráfego.
  • Exemplo: Istio e Linkerd.

2. Padrões de Resiliência

Circuit Breaker

  • Evita que falhas em um serviço se propaguem para outros, “desligando” chamadas a serviços não responsivos.
  • Exemplo: O Hystrix, da Netflix, é uma implementação popular.

Retry e Backoff Exponencial

  • Tenta repetir a requisição em caso de falha, aumentando o tempo entre tentativas para evitar sobrecarregar o sistema.

Bulkhead (Compartimentos Estanques)

  • Separa recursos para evitar que falhas em uma parte do sistema afetem outras.
  • Exemplo: Se um serviço de pagamento estiver sobrecarregado, ele não deve afetar a operação de login.

3. Padrões de Dados e Armazenamento

Database per Service

  • Cada microserviço tem seu próprio banco de dados para evitar dependências diretas.
  • Isso melhora escalabilidade, mas pode gerar desafios de consistência.

Event Sourcing

  • Os dados são armazenados como uma sequência de eventos em vez de estados mutáveis.
  • Facilita a rastreabilidade e auditoria, além de permitir reconstrução do estado.

CQRS (Command Query Responsibility Segregation)

  • Separa operações de leitura e escrita para otimizar desempenho.
  • Normalmente usado com Event Sourcing.

4. Padrões de Comunicação Assíncrona

Publisher-Subscriber (Pub/Sub)

  • Um serviço publica eventos em um broker (como Kafka, RabbitMQ), e outros serviços assinam para receber atualizações.
  • Desacopla os serviços, melhorando escalabilidade.

Event Notification

  • Um serviço apenas emite um evento informando que algo aconteceu, mas não se preocupa com quem vai consumi-lo.
  • Exemplo: Um serviço de pedidos pode publicar um evento "PedidoCriado", e os serviços de pagamento e estoque podem reagir a ele.

Event-Carried State Transfer

  • Um serviço publica eventos contendo dados completos do estado atual para que outros serviços não precisem consultar diretamente.

5. Padrões de Segurança

Access Token (OAuth2, JWT)

  • Usa tokens para autenticação e autorização entre serviços.

Sidecar Pattern

  • Um container auxiliar que adiciona funcionalidades como logging, segurança e proxy de comunicação.
  • Exemplo: Istio usa Sidecar para gerenciamento de tráfego.

API Rate Limiting

  • Restringe o número de requisições para evitar ataques DDoS.

6. Padrões de Gerenciamento e Monitoramento

Observability (Logs, Metrics, Tracing)

  • Usa ferramentas como Prometheus, ELK, OpenTelemetry para monitorar microserviços.

Strangler Pattern

  • Ajuda a migrar de um monólito para microserviços gradualmente, substituindo partes do sistema sem interromper o funcionamento.

Conclusão

Esses padrões ajudam a projetar microserviços mais escaláveis, resilientes e seguros. A escolha depende das necessidades do sistema e dos desafios específicos enfrentados.
