Event Sourcing

Event Sourcing é um padrão arquitetural onde o estado de um sistema é derivado de uma sequência de eventos em vez de armazenar diretamente o estado atual em um banco de dados tradicional.
Ao invés de simplesmente armazenar a última versão dos dados, o Event Sourcing mantém um histórico completo de todas as mudanças feitas no sistema na forma de eventos imutáveis. Isso permite reconstruir o estado do sistema a qualquer momento, fornecendo rastreabilidade e auditabilidade total.

Como Funciona o Event Sourcing?

1️⃣ Captura de Eventos

Cada ação que modifica o sistema é registrada como um evento. Por exemplo, em um sistema bancário, ao invés de armazenar apenas o saldo da conta, registramos eventos como:

  • “Conta Criada”
  • “Depósito Realizado”
  • “Saque Efetuado”

Esses eventos contêm os dados necessários para descrever a mudança (ex: valor do depósito, data, usuário que fez a ação).

2️⃣ Armazenamento dos Eventos

Os eventos são armazenados de forma ordenada e imutável em um repositório chamado Event Store. Isso é diferente de um banco de dados tradicional, pois os eventos nunca são alterados ou excluídos, apenas novos eventos são adicionados.

3️⃣ Reconstrução do Estado

Quando o sistema precisa saber o estado atual de um objeto, ele reconstitui os dados a partir dos eventos. Por exemplo, para saber o saldo de uma conta bancária, basta somar todos os eventos de “Depósito” e subtrair os eventos de “Saque”.

4️⃣ Publicação de Eventos para Outros Sistemas

Os eventos podem ser publicados para outros serviços, permitindo que diferentes partes do sistema reajam a mudanças de estado sem depender diretamente umas das outras. Isso é útil em arquiteturas event-driven (orientadas a eventos).

Exemplo Prático

Imagine um sistema de pedidos de e-commerce usando Event Sourcing.

1️⃣ Eventos armazenados no Event Store:

TimestampEventoDados
10:00 AMPedidoCriado{ pedidoId: 123, cliente: João }
10:05 AMProdutoAdicionado{ pedidoId: 123, produto: Camisa }
10:10 AMProdutoAdicionado{ pedidoId: 123, produto: Sapato }
10:15 AMPedidoConfirmado{ pedidoId: 123 }
10:20 AMPagamentoAprovado{ pedidoId: 123, valor: R$200 }

2️⃣ Como reconstruir o estado do pedido?

Se quisermos saber o estado atual do pedido 123, podemos percorrer os eventos na ordem em que ocorreram e reconstruir o estado final:

  • O pedido foi criado para o cliente João.
  • Foram adicionados os produtos Camisa e Sapato.
  • O pedido foi confirmado.
  • O pagamento de R$200 foi aprovado.

Dessa forma, o estado do pedido é derivado da sequência de eventos, em vez de ser simplesmente salvo como um registro estático no banco de dados.

Benefícios do Event Sourcing

✅ Histórico Completo

  • Como todos os eventos são armazenados, é possível rastrear exatamente o que aconteceu no sistema e quando.

✅ Auditoria e Compliance

  • Facilita auditorias e investigações, pois o histórico de mudanças é preservado.

✅ Recuperação e Depuração

  • Se houver um erro, é possível reconstituir o estado passado para encontrar a causa do problema.

✅ Escalabilidade

  • Eventos podem ser armazenados de forma distribuída e processados assincronamente.

✅ Integridade dos Dados

  • Como os eventos são imutáveis, não há risco de perda ou corrupção de dados.

✅ Facilidade para CQRS (Command Query Responsibility Segregation)

  • Permite separar as operações de escrita (armazenando eventos) das operações de leitura (reconstruindo projeções de estado).

Desafios do Event Sourcing

❌ Complexidade na Implementação

  • Requer um Event Store eficiente e uma estratégia para reconstrução do estado.

❌ Gerenciamento de Evolução de Eventos

  • Se a estrutura de um evento mudar, é necessário migrar os eventos antigos ou criar mecanismos de compatibilidade.

❌ Consulta de Dados Pode Ser Mais Difícil

  • Como o estado do sistema não é armazenado diretamente, consultar dados pode exigir processamento adicional.

❌ Grande Volume de Eventos

  • Sistemas grandes podem acumular bilhões de eventos, tornando necessário armazenamento otimizado e técnicas como snapshots (armazenar estados intermediários para evitar processar todos os eventos desde o início).

Diferença entre Event Sourcing e Event-Driven Architecture

CaracterísticaEvent SourcingEvent-Driven Architecture
PropósitoPersistir eventos e reconstruir estadoReagir a eventos de forma assíncrona
ArmazenamentoEventos armazenados como fonte de verdadeEventos geralmente descartados após processamento
Rastreamento do EstadoSim, é possível reconstruir o estado atual a partir dos eventosNão necessariamente, apenas reage aos eventos
ExemploConta bancária que armazena todas as transações como eventosServiço que recebe eventos de pagamento e envia e-mails de confirmação

Muitas vezes, Event Sourcing e Event-Driven Architecture são usados juntos para criar sistemas escaláveis e reativos.

Ferramentas para Event Sourcing

Event Stores

  • EventStoreDB
  • Apache Kafka
  • DynamoDB Streams
  • Azure Event Hubs
  • PostgreSQL (com JSONB para eventos)

Frameworks

  • Microsoft Orleans
  • Axon Framework (Java)
  • Marten (C#/.NET)
  • NEventStore (.NET)

Conclusão

Event Sourcing é uma abordagem poderosa para armazenar e processar eventos como fonte de verdade. Ele permite que os sistemas sejam mais confiáveis, escaláveis e rastreáveis, mas também adiciona complexidade ao desenvolvimento.

Se bem projetado, Event Sourcing pode trazer grandes benefícios para sistemas financeiros, e-commerce, logística e outros domínios onde rastreabilidade e consistência são essenciais.
