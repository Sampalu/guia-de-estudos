CQRS (Command Query Responsibility Segregation)

CQRS (Segregação de Responsabilidade entre Comando e Consulta) é um padrão arquitetural que separa operações de leitura (Query) e escrita (Command) em um sistema. O objetivo principal é melhorar a escalabilidade, desempenho e segurança, evitando que consultas afetem a performance das operações de escrita e vice-versa.

O Problema que o CQRS Resolve

Em uma arquitetura tradicional, geralmente utilizamos um modelo único para leitura e escrita, onde o mesmo banco de dados e os mesmos objetos de domínio são usados para buscar e modificar informações. Isso pode gerar problemas como:

✅ Concorrência: Grandes volumes de leitura podem impactar a performance de operações de escrita.
✅ Escalabilidade: Diferentes requisitos de leitura e escrita dificultam a otimização do banco de dados.
✅ Complexidade em domínios ricos: Nem sempre os dados usados para escrever são os mesmos necessários para leitura.

Exemplo:
Imagine um sistema de e-commerce onde temos um modelo Pedido que é atualizado constantemente. A leitura dos detalhes do pedido deve ser rápida, mas as operações de atualização exigem validações e lógica de negócio complexa. O modelo de leitura pode ser simples, enquanto o de escrita pode ser mais sofisticado.

Como o CQRS Funciona

A ideia central do CQRS é separar operações de leitura e escrita, utilizando diferentes modelos e, em alguns casos, diferentes bancos de dados.

  • Comandos (Commands) → Usados para escrita e modificação de estado do sistema.
  • Consultas (Queries) → Usadas apenas para leitura, sem afetar o estado do sistema.

Diagrama básico do CQRS:

                ┌────────────────────┐
                │     Usuário        │
                └────────┬───────────┘
                         │
             ┌───────────▼───────────┐
             │      API Gateway      │
             └───────────┬───────────┘
                ┌────────┴─────────────┐
                │                      │
      ┌─────────▼──────────┐ ┌─────────▼─────────┐
      │ Command Handler    │ │ Query Handler     │
      │ (Escrita)          │ │ (Leitura)         │
      └─────────┬──────────┘ └────────┬──────────┘
                │                     │
      ┌─────────▼───────┐   ┌─────────▼────────┐
      │  Banco de Dados │   │  Banco de Dados  │
      │  de Escrita     │   │  de Leitura      │
      └─────────────────┘   └──────────────────┘

Implementação do CQRS

Existem diversas formas de implementar CQRS. As mais comuns incluem:

✅ 1. Separação Lógica
O mesmo banco de dados é utilizado, mas consultas e comandos usam repositórios diferentes.

✅ 2. Separação Física
Diferentes bancos de dados são usados:

  • Banco de Escrita (ex: PostgreSQL)
  • Banco de Leitura (ex: MongoDB, ElasticSearch)

✅ 3. Eventual Consistency
Quando usamos dois bancos distintos, pode haver um pequeno atraso entre a gravação e a atualização dos dados disponíveis para leitura.

Exemplo Prático

Vamos considerar um sistema de pedidos de um e-commerce:

1. Escrita (Command) Quando um novo pedido é criado, ele é salvo no Banco de Escrita:

{
  "pedidoId": "123",
  "cliente": "João",
  "status": "Pendente",
  "itens": [
    { "produto": "Notebook", "quantidade": 1, "preco": 5000 }
  ]
}

2. Leitura (Query) O usuário quer visualizar seus pedidos. Em vez de buscar no banco principal (que pode estar sobrecarregado), a informação é recuperada de um Banco de Leitura otimizado para buscas rápidas:

{
  "pedidoId": "123",
  "cliente": "João",
  "status": "Pendente",
  "resumo": "1x Notebook - R$5000"
}

3. Sincronização
O CQRS pode ser combinado com Event Sourcing para garantir que os dados de leitura sejam atualizados corretamente. Um evento como PedidoCriado pode ser publicado em uma fila e processado para atualizar o banco de leitura.

Vantagens e Desvantagens do CQRS

🔥 Vantagens⚠️ Desvantagens
Melhor escalabilidadeMaior complexidade inicial
Otimização de leitura e escrita separadamentePode aumentar latência em sistemas mal projetados
Facilidade na manutenção de códigoRequer sincronização entre bancos de leitura e escrita
Segurança: permite restringir escrita e leitura separadamentePode precisar de Eventual Consistency

Quando Usar CQRS?

✅ Quando há grande volume de leitura e escrita em um sistema.
✅ Quando operações de leitura precisam ser otimizadas e diferenciadas das de escrita.
✅ Quando queremos segurança extra, impedindo que consultas modifiquem dados acidentalmente.
✅ Quando há necessidade de escalabilidade horizontal (dividir cargas de leitura e escrita).

⚠️ Quando NÃO Usar:
❌ Em sistemas pequenos ou CRUDs simples.
❌ Quando a complexidade adicionada não justifica os benefícios.

Conclusão

O CQRS é um padrão poderoso para sistemas distribuídos que precisam escalar e otimizar leituras e escritas. Ele pode ser combinado com Event Sourcing para garantir consistência e rastreabilidade, mas também introduz complexidade. O segredo é avaliar se os benefícios justificam a adoção no seu contexto.
