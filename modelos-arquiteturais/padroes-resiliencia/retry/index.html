Retry (Tentativa de Repetição)

Se uma operação é malsucedida devido a uma falha temporária (como um timeout ou erro de rede), o sistema pode tentar novamente após um intervalo.
Exemplo: Um serviço tentando se conectar a um banco de dados pode repetir a tentativa algumas vezes antes de falhar definitivamente.
Categories:
  • Cloud

  3 minute read  

O Retry é um padrão de resiliência que permite a repetição de uma operação malsucedida antes de considerar a falha definitiva. Ele é útil para lidar com falhas temporárias, como timeouts, problemas de rede, ou serviços sobrecarregados, garantindo que pequenas falhas não causem interrupções no sistema.

Quando Usar Retry?

✅ Falhas temporárias → Como um pequeno problema de conectividade.
✅ Serviços intermitentes → Se um serviço estiver sobrecarregado e puder responder corretamente após um curto período.
✅ Time-outs transitórios → Se um request para um serviço externo demorar mais do que o esperado.
✅ Erros recuperáveis → Exemplo: HTTP 500 (Erro interno do servidor), 503 (Serviço indisponível), 408 (Timeout).

🚫 Quando NÃO usar Retry?
❌ Em falhas permanentes → Se uma senha estiver errada ou um arquivo não existir, repetir a requisição não vai ajudar.
❌ Quando pode causar mais sobrecarga → Se um serviço já está sobrecarregado, o Retry excessivo pode piorar a situação (nesse caso, combinar com Circuit Breaker pode ser melhor).

Estratégias de Retry

1️⃣ Retry Imediato (Instantâneo)

  • Simplesmente refaz a tentativa imediatamente após uma falha.
  • Problema: Pode sobrecarregar o serviço rapidamente se houver muitas falhas sucessivas.
  • Uso: Apenas para casos onde o serviço está falhando ocasionalmente.

2️⃣ Retry com Intervalo Fixo

  • Aguarda um tempo fixo antes de tentar novamente.
  • Exemplo: Se uma requisição falha, espera 3 segundos antes da próxima tentativa.
@Retry(name = "pagamentoRetry", maxAttempts = 3, waitDuration = 3000)
public String processarPagamento() {
    return restTemplate.getForObject("https://api.pagamento.com/processar", String.class);
}

🔹 Problema: Se muitas requisições falharem, todas vão continuar tentando ao mesmo tempo, podendo causar um “efeito tempestade” no serviço.

3️⃣ Retry Exponencial (Exponential Backoff)

  • O tempo de espera entre tentativas aumenta exponencialmente para reduzir a carga no sistema.
  • Exemplo: Espera 2 segundos antes da primeira repetição, depois 4 segundos, depois 8, etc.
  • Evita sobrecarga, pois espaça melhor as requisições.

Padrão usado por APIs como AWS, Google Cloud e Azure!

const retry = require('async-retry');

async function fetchData() {
    await retry(async () => {
        let response = await fetch('https://api.exemplo.com/data');
        if (!response.ok) throw new Error('Falha na requisição');
        return response.json();
    }, {
        retries: 5,
        minTimeout: 1000, // Começa com 1 segundo
        maxTimeout: 10000, // Máximo de 10 segundos entre tentativas
    });
}

🔹 Vantagem: Reduz a chance de sobrecarga, pois dá mais tempo para o serviço se recuperar.

4️⃣ Retry com Jitter (Exponential Backoff + Aleatoriedade)

  • Adiciona um fator aleatório no tempo de espera para evitar que todas as requisições falhas tentem novamente ao mesmo tempo.
  • Exemplo: Se o tempo de espera seria 4 segundos, ele pode variar entre 3 e 5 segundos.

🔹 Uso recomendado para sistemas distribuídos e grandes cargas!

RetryConfig config = RetryConfig.custom()
    .maxAttempts(5)
    .waitDuration(Duration.ofMillis(1000))
    .intervalFunction(IntervalFunction.ofExponentialRandomBackoff(1000, 2))
    .build();

Bibliotecas para implementação de Retry em Diferentes Tecnologias

  • Java/Spring Boot → Resilience4j
  • .NET → Polly
  • Node.js → async-retry, axios-retry
  • Python → Tenacity

Conclusão

O padrão Retry é essencial para lidar com falhas temporárias em serviços distribuídos, aumentando a resiliência do sistema. A escolha da estratégia correta (fixo, exponencial, jitter) evita sobrecarga e melhora a experiência do usuário.

Melhor prática: Combinar Retry com Circuit Breaker para evitar tentar repetidamente um serviço que já está falhando de forma permanente.
